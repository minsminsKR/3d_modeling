# Individual temple stone placement: CPU experiment notes

This is an approximate layout study, not game code. Run `python stone_layout_cpu_probe.py stone_layout_cpu_probe.json` on Python 3.11. The script sets its own Windows process to BelowNormal priority. It uses a 3.4 m by 31 m path in a local frame centered on the existing approach; world z is this frame shifted by -5 m. The parameters and seed are provisional.

- Each stone is a 2D oriented ellipse. Edge x extents must remain inside the physical footstep region with a continuous z-varying margin. z extents are inside the path ends. Neighboring ellipses must have an 8 mm separation along a shared separating axis from a fixed set of 32 directions. This can conservatively reject viable disjoint pairs, but any accepted pair is separated as ellipses. It says nothing about whether a real irregular mesh fits within the ellipse, height interactions, or tilt.
- A staggered grid with jitter generates candidates; a second pass tries additional large ellipses; a third optional pass tries smaller ellipses. They produce 198 / 217 / 352 hypothetical stones. Interior and exterior coverage and raster overlap are computed at 5 cm, and use the 0.8m center strip to report maximum consecutive fully empty sample rows. A center-strip empty-row count is not a Euclidean clearance, footstep or accessibility test.
- Ellipse half axes are provisional large [0.27,0.325] x [0.225,0.285] m and small [0.12,0.18] x [0.105,0.155] m. Because actual stone 3D shape and pivot are unknown until web review and Blender preparation, do not treat these as physical model dimensions or candidate approval. A clustered pattern or artifacts are possible even if metrics pass; review near/far views and while moving.
- Dense candidate estimates 352 meshes with hypothetical uniform 3000/1200/400-triangle LODs, giving at most 1,056,000/422,400/140,800 triangles when all use that one LOD and all are visible; actual triangles, draw calls and timing need measurement. Bounds-safe spatial chunking of shared mesh/material with LOD groups may improve overhead versus 352 individual groups. It trades fewer renderers for chunk-wide LOD selection: profile both in the actual scene, preserve light probes, bounds, shadow behavior and destruction. Include 32-bit index support or bounded 16-bit chunks as needed.
- The initial deterministic repeat uses Python `random.Random` in the exact current interpreter. Reimplementing with `System.Random` in Unity will not produce the same layout; specify a portable integer PRNG/hash and golden seed outputs or bake editable placement data before relying on cross-machine/checkpoint reproducibility. Avoid consuming gameplay RNG.
- Proposed verification: actual footprint mesh vs collision test (including rotated/scaled mesh bounds and overhang), no geometry protrusion from the 3.4x31m footstep area, dense center with naturally feathered sides, preserve unchanged `Stone approach` enabled state/bounds for `IsStoneApproach`, unchanged ground physics and no added collision, bounded height comparable to flat player feet, preserve altar and puddle placements, material/UV PBR and LOD bounds/transition screenshots, cleanup and original renderer-state restoration. Compare front, low, side/edge, seam/close and flashlight frames plus a walking-camera sweep. Measure draw calls, visible triangles and GPU cost separately from output-space screenshots. Existing `TempleForestPathTests` hardcode current tile ownership/counts, so replace those assertions with behavior-preserving checks when implementation actually changes.
- The 5cm cell-center sampling estimated 0% overlap; it cannot prove that no small gaps/overlap exist, and real generated stones may violate the ellipse assumption. Visual approval is separate.
